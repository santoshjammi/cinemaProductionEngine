# PROMETHEUS-004 — Execution Intermediate Representation (EIR)

> The EIR is the central contract of PROMETHEUS. Everything upstream produces it; everything downstream consumes it. Adapters never touch the PKP directly. This document defines the EIR's schema, its invariants, its versioning, and its serialization.

---

## 1. Purpose

Define, at engineering precision:

- What the EIR *is* and what it *is not*.
- The EIR's schema (nodes, dependencies, bindings, provenance stubs, metadata).
- The EIR's invariants (what must hold for an EIR to be valid).
- The EIR's versioning (how the schema evolves without breaking adapters).
- The EIR's serialization (language-neutral formats).
- The EIR's relationship to the PKP, to adapters, and to the execution report.

The EIR is the architectural enforcement of adapter independence (`010` §10.1): adapters consume the EIR, never the PKP. A new adapter is written against the EIR, not against the PKP.

---

## 2. What the EIR Is

The EIR is a **language-neutral, versioned, deterministic DAG** that describes everything an adapter needs to execute one unit of work, plus the dependencies between units.

```
PKP (009)
   │
   │  PROMETHEUS compiles
   ▼
EIR (this doc)
   │
   │  adapters consume
   ▼
Adapter invocations
   │
   │  events + outputs
   ▼
Execution report + ATLAS
```

The EIR is **not**:

- The PKP. The PKP is the input; the EIR is the compiled execution contract.
- A creative artifact. The EIR contains no creative decisions (L-15); it contains only the executable projection of the PKP.
- A schedule. The schedule is a separate artifact (produced by the scheduler from the EIR).
- An event stream. Events are emitted during execution; the EIR is static once emitted.
- A report. The report is assembled after execution; the EIR is an input to the report.

The EIR **is**:

- The single artifact an adapter reads to execute a node.
- The basis for determinism (same EIR + same adapter versions ⇒ same outputs).
- The basis for cache keys (`(EIR node hash, adapter id, adapter version, seed, config hash)`).
- The basis for provenance (every output's provenance references its EIR node).
- The basis for resume (a checkpoint references the EIR + the per-node state).

## 3. EIR Schema

The EIR is a directed acyclic graph of **nodes**. Each node describes one unit of executable work. The schema is defined here in a language-neutral form (JSON Schema); the serialization format is decided by ADR (candidate 0003).

### 3.1 Top-level EIR structure

```
EIR {
  eir_id        : EIRId          // deterministic hash of the EIR contents
  eir_version   : SemVer        // the EIR schema version (this spec)
  pkp_reference : PKPReference  // the PKP this EIR was compiled from
  compiled_at   : Timestamp      // wall-clock (recorded, not used in hashes)
  compiler_version : SemVer     // the PROMETHEUS version that compiled this EIR
  nodes         : List<Node>     // the executable units
  edges         : List<Edge>     // the dependency edges
  metadata      : Metadata       // global EIR metadata
}
```

### 3.2 Node structure

A node is one unit of executable work. Every PKP artifact maps to ≥1 node (compilation closure, Invariant 7.1 from `DESIGN/001`).

```
Node {
  node_id        : NodeId         // stable, deterministic (e.g., "scene-3.image-1")
  pkp_artifact   : ArtifactRef    // the PKP artifact this node renders
  capability     : Capability     // the capability required (e.g., "image-generation")
  adapter_binding : AdapterBinding // the resolved adapter to invoke
  inputs         : List<Input>    // the inputs to the adapter (from PKP + parent outputs)
  parameters     : Parameters     // adapter-specific parameters (from PKP)
  seed           : Option<Seed>    // the seed for deterministic providers (from PKP)
  determinism    : DeterminismMode // seed-based | recorded-output
  fallback       : Option<AdapterBinding> // the fallback adapter (from PKP + registry)
  validation     : ValidationSpec  // what to check on the output before emission
  condition      : Option<Condition> // gate execution on a condition (PKP-declared)
  skip           : Option<SkipSpec>   // PKP-declared skip with rationale
  provenance_stub : ProvenanceStub   // the provenance to stamp on the output
  metadata       : NodeMetadata
}
```

### 3.3 Edge structure

An edge is a dependency: "node A depends on node B's output."

```
Edge {
  from_node  : NodeId    // the dependent node
  to_node    : NodeId    // the dependency (must complete first)
  edge_kind  : EdgeKind  // dependency | data-flow | ordering
  metadata   : EdgeMetadata
}
```

The EIR's edges form a DAG. Cycles are invalid (dependency closure, Invariant 7.1).

### 3.4 AdapterBinding

```
AdapterBinding {
  adapter_id     : AdapterId     // the capability-registry id
  adapter_version : SemVer       // the adapter's version
  capability     : Capability    // the capability this adapter satisfies
  config         : Config        // adapter-specific config (no secrets)
}
```

AdapterBindings do **not** contain secrets. Secrets are resolved at invocation time from the configuration (S24) and the security subsystem (S25), never stored in the EIR.

### 3.5 Input

```
Input {
  name     : String          // the input's logical name (e.g., "scene_image")
  source   : InputSource      // pkp-artifact | parent-output | config | constant
  ref      : Ref              // the reference (artifact id, node id, config key, or value)
  type     : TypeRef          // the expected type
}
```

Inputs are references, not embedded values. Large assets are referenced by id; the adapter resolves them via ATLAS or the local cache.

### 3.6 DeterminismMode

```
DeterminismMode : "seed-based" | "recorded-output"
```

- `seed-based`: the adapter is deterministic given a seed; the seed is in the node.
- `recorded-output`: the adapter is irreducibly non-deterministic; the runtime records the output and replays it (`010` §9.3).

### 3.7 ValidationSpec

```
ValidationSpec {
  checks    : List<Check>    // the checks to run on the output
  on_fail   : OnFailAction   // retry | fallback | fail | gap
}

Check : {
  kind     : CheckKind      // resolution | duration | format | hash | custom
  params   : CheckParams
}
```

### 3.8 ProvenanceStub

```
ProvenanceStub {
  pkp_artifact   : ArtifactRef
  pkp_hash       : Hash
  eir_node_id    : NodeId
  adapter_binding : AdapterBinding
  seed           : Option<Seed>
  parent_outputs : List<NodeId>   // the nodes whose outputs this output depends on
}
```

The stub is completed at emission time with the timestamp and the output hash (`DESIGN/013`).

### 3.9 Metadata

```
NodeMetadata {
  tags        : List<String>   // free-form tags (e.g., "scene-3", "image")
  priority    : Int             // scheduling priority (PKP-declared)
  budget      : Option<ResourceBudget>  // compute/memory budget
  estimated_duration : Option<Duration> // for scheduling
}

EIRMetadata {
  domain      : String         // "cinema" | "book" | "game-level" | ...
  profile     : String         // the config profile used
  plugin_set_hash : Hash       // the plugins active at compile time
  config_hash : Hash           // the config hash
}
```

## 4. EIR Invariants

An EIR is **valid** iff all of the following hold. An invalid EIR cannot be scheduled; the validator emits diagnostics.

### 4.1 Compilation closure

Every PKP artifact maps to ≥1 EIR node. Artifacts the PKP marks `skipped` are represented as nodes with `skip` set; they are not omitted.

### 4.2 Dependency closure

Every EIR edge's `to_node` exists in the EIR. The edge graph is acyclic. Cycles emit `dependency-cycle` diagnostics.

### 4.3 Adapter binding closure

Every executable node (non-skip) has an `AdapterBinding` whose `adapter_id` resolves in the capability registry. Unresolved bindings emit `unresolved-adapter` diagnostics.

### 4.4 Input closure

Every input `ref` resolves: PKP artifact refs resolve to PKP artifacts; parent-output refs resolve to other EIR nodes; config refs resolve in the configuration; constants are literals. Unresolved inputs emit `unresolved-input` diagnostics.

### 4.5 Determinism closure

Every executable node has a `DeterminismMode`. `seed-based` nodes have a seed (or the adapter declares itself seed-free and deterministic). `recorded-output` nodes have a recorded-output reference (after first render) or are marked `first-render-required`.

### 4.6 Provenance closure

Every executable node has a `ProvenanceStub`. The stub's `parent_outputs` are a subset of the node's `to_node` edges.

### 4.7 No-secret closure

The EIR contains no secrets. `AdapterBinding.config` contains only non-secret config. Secrets are resolved at invocation time.

### 4.8 Versioning closure

The EIR carries `eir_version`, `compiler_version`, and `pkp_reference`. An adapter can reject an EIR whose `eir_version` it does not support.

## 5. EIR Versioning

The EIR schema evolves. Evolution is governed by semantic versioning:

| Change type | Version bump | Adapter impact |
|---|---|---|
| Add an optional field | Minor | None — adapters ignore unknown optional fields. |
| Add a required field | Major | Adapters must be updated. |
| Remove a field | Major | Adapters must be updated. |
| Change a field's semantics | Major | Adapters must be updated. |
| Change a field's type | Major | Adapters must be updated. |

Major-version bumps require a migration path: the compiler can emit EIRs in both the old and new major version for a deprecation period. Adapters declare the EIR versions they support; the runtime refuses to dispatch to an adapter that does not support the EIR's major version.

Minor-version bumps are additive and non-breaking. Adapters ignore fields they do not understand.

Patch-version bumps are clarifications of this document, not schema changes.

## 6. EIR Serialization

The EIR is serializable to language-neutral formats. The primary format is JSON (human-readable, universally parseable). A binary format (MessagePack, Protobuf, or a custom format) is an ADR candidate (0003) for size-sensitive or throughput-sensitive paths.

Serialization rules:

- The serialization is **deterministic**: the same EIR serializes to the same bytes, byte-identical. Field order is fixed; map keys are sorted lexicographically; floating-point is normalized.
- The serialization is **versioned**: the `eir_version` is the first field.
- The serialization is **self-describing**: the schema is discoverable from the `eir_version`.
- The serialization **excludes secrets**: the no-secret closure (4.7) holds in serialization.

## 7. EIR and Determinism

The EIR is the basis for determinism (Invariant 7.1 from `DESIGN/001`):

- The EIR's `eir_id` is a deterministic hash of its contents (excluding `compiled_at` and other non-deterministic metadata).
- Two compilations of the same PKP + same compiler version + same config + same plugin set produce byte-identical EIRs (and therefore the same `eir_id`).
- The cache key for a node is `(node hash, adapter id, adapter version, seed, config hash)`. The node hash is a deterministic hash of the node's contents.
- The schedule is a pure function of the EIR + scheduler config.
- The outputs are a pure function of the EIR + adapter versions (with the recorded-output fallback for non-deterministic providers).

Non-deterministic metadata (`compiled_at`, per-step durations, wall-clock timestamps) is recorded in events and the report, but does not enter the `eir_id` or any cache key.

---

## 8. EIR and the PKP

The EIR is a **projection** of the PKP. It is not a copy:

- The PKP contains creative decisions (CIR-derived); the EIR contains only their executable projection.
- The PKP contains the full artifact graph; the EIR contains only the executable units and their dependencies.
- The PKP is the input; the EIR is the compiled contract.
- The PKP is read-only for PROMETHEUS (L-14); the EIR is derived and disposable (it can be regenerated from the PKP).

The EIR never contains creative content that is not in the PKP (L-15). If the PKP is silent on a detail the EIR needs, the compiler emits a `rendering-gap` diagnostic and a skip node, not an invented value.

---

## 9. EIR and Adapters

Adapters consume the EIR. An adapter's contract is:

```
Adapter.invoke(node : Node, inputs : ResolvedInputs) → AdapterResult
```

The adapter receives:
- The node (its binding, parameters, seed, validation spec, provenance stub).
- The resolved inputs (the actual values the inputs reference).

The adapter returns:
- A result: success (with output) | failure (with classification) | gap (with missing-detail report).

The adapter **never**:
- Reads the PKP directly.
- Modifies the EIR.
- Makes creative decisions (L-15).
- Calls GENESIS, ORACLE, or the human.
- Writes to ATLAS (the Asset Emission Service does that).

The adapter **does**:
- Invoke the provider (local or cloud) per its binding.
- Run the ValidationSpec checks on its output.
- Record its version, the seed, and the invocation params (for provenance).
- Classify its own failures (recoverable / retryable / fatal).

---

## 10. EIR and the Execution Report

The execution report (`DESIGN/013`) includes the EIR (or a reference to it). This allows ORACLE to validate outputs against the PKP using only the report + provenance: the report contains the EIR, the schedule, the events, the diagnostics, and the output manifest; ORACLE cross-checks the EIR against the PKP and the outputs against the EIR.

## 11. EIR Lifecycle

```
PKP (frozen)
   │
   │  Stage 1: Load
   ▼
LoadedPKP
   │
   │  Stage 2: Validate
   ▼
ValidatedPKP
   │
   │  Stages 3-4: Resolve
   ▼
ResolvedPKP
   │
   │  Stages 5-7: Timeline, Plan, Build Graph
   ▼
ExecutionGraph
   │
   │  Stage 8: Emit EIR
   ▼
EIR (immutable from here)
   │
   │  Stage 9: Schedule
   ▼
Schedule + EIR
   │
   │  Stage 10: Execute (adapters consume EIR nodes)
   ▼
Outputs + Events
   │
   │  Stages 12-13: Emit + Report
   ▼
ExecutionReport (includes EIR) ──► ATLAS
```

The EIR is **immutable** from Stage 8 onward. No subsystem modifies it. The scheduler reads it; the adapters read it; the report includes it.
